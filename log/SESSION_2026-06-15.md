### Root cause
Two distinct aiohttp failure modes make the 120s `ClientTimeout` unreliable:

1. **aiohttp 3.13 cross-loop bug.** `ClientSession()` requires a running event loop at construction. ZyteAPI's sync wrapper runs calls inside `loop.run_until_complete`. When the session's `_loop` differs from the running loop (which can happen across our resource-init / call boundary), aiohttp's `BaseTimerContext.__enter__` fails with `RuntimeError("Timeout context manager should be used inside a task")` **immediately** — not after the configured timeout. Verified by reading `aiohttp/helpers.py:678` and tracing the call path through `aiohttp/client.py:632` → `with timer:`.

2. **Genuine socket hang.** When a Zyte call hangs in `kevent` (verified via `sample` on the stuck worker: Thread_27151032 in `kevent`, main thread in `_pthread_cond_wait`), the timer is unreliable and the caller blocks indefinitely. The "all keys exhausted" message that the user saw was masking this — every key tried the same hung request, every one failed, then the rotation logic reported exhaustion.

### Why earlier fixes didn't catch this
- PR #22 added the per-call `ClientTimeout(total=120)`, but aiohttp's cross-loop bug means the timer can fail to engage without raising an obvious error.
- The previous tests mocked `aiohttp.ClientSession`, so they never exercised the real timeout machinery. (Rule 9 violation — mock-based tests cannot detect contract changes in the dependency.)
- The "all keys exhausted" message was a misleading wrap of a timeout — the actual cause was hidden.

### Fix
`ZyteSessionResource._try_get` now submits each `client.get()` to a bounded `ThreadPoolExecutor` and applies `future.result(timeout=self._api_timeout)`. This is a Python-level hard deadline independent of aiohttp internals.

Plus:
- A new `except RuntimeError` branch in `_try_get` catches the aiohttp cross-loop bug and treats it as a timeout.
- `get()` now distinguishes "all keys timed out" from "all keys exhausted" in the final error message.
