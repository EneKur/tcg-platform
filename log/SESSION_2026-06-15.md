`2026-06-15-zyte-key1-bug`

## Goal
User reported that `complete_eu_pipeline` failed again with a red error.

## Done

### Diagnosis (systematic-debugging skill)
- **Symptom:** `bronze_eu_orchestrator` step failed with `RuntimeError: All Zyte API keys exhausted (KEY1, KEY2)`. `exchange_rates_job` ran successfully in parallel; the failure was in one of the eBay scrapes.
- **Three root causes** conspired to fail the run (none of which were "actual rate limiting" — they were code bugs):
  1. **`zyte_resources.py:109` read `ZYTE_API_KEY` (no suffix) for `i=1`**, so `ZYTE_API_KEY1` in `.env` was silently dropped. The user thought they had 3 keys; the code only loaded 2.
  2. **`client.get()` was called with the default `handle_retries=True`**, so ZyteAPI's built-in retry policy retried 402 "over-user-limit" twice per dead key before raising. Pure waste on a key that cannot succeed this month.
  3. **No per-key "dead for the month" state.** A key that 402'd on the first call was retried on every subsequent call in the same process, burning more monthly quota each time.

### Fix (TDD: 3 RED → 3 GREEN → 163 green)
- `_read_api_keys` now reads `ZYTE_API_KEY1`, `ZYTE_API_KEY2`, ... uniformly. Old code had `f"ZYTE_API_KEY{i if i > 1 else ''}"` — the `i > 1` branch was a backwards-compat shim for the suffix-less legacy var that no longer exists.
- `_try_get` passes `handle_retries=False` to `client.get()` so the wrapper owns retry/rotation decisions.
- `get()` tracks `_dead_keys: set[int]`. A 402 (`RequestError.status == 402`) marks the key as dead for the lifetime of the resource; subsequent `get()` calls skip dead keys entirely.
- Added `RequestError` to the top-level import in `zyte_resources.py` (was previously imported inside the loop — refactor lifted it).

### Tests added
