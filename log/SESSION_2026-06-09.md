# Session Log — 2026-06-09 (M8-T3 quarantine reconciliation)

## Branch
`2026-06-09-m8-t3-quarantine-reconcile` (merged via PR #15)

## What was done

Added quarantine reconciliation to the silver EU orchestrator so that
eBay sold-listing rows quarantined because their `card_id` was unknown
at the time silver ran (e.g. a freshly-shipping OP16 card scraped
before the OP16 card images were synced) now have a path to leave
quarantine.

### Approach

A new `reconcile_quarantine.py` module exposes a pure helper
`_reconcile_region(minio, region)` plus two Dagster assets
(`reconcile_quarantine_de`, `reconcile_quarantine_uk`) and two
corresponding jobs. The `silver_eu_orchestrator` body was updated to
call the two new jobs before the existing silver calls.

For each parquet in `tcg-silver/quarantine/{region}/`, the helper:
1. Reads the row's `card_id`.
2. Re-validates against the **current** `tcg-bronze/cards/` set
   (freshly loaded on every call).
3. If valid → batch-deletes the quarantine parquet via
   `MinioClientResource.remove_objects()` (the only delete API
   available; there is no singular `remove_object`).
4. If still invalid → leaves the file alone.

The next silver run re-reads the (immutable) bronze parquet for the
promoted row, re-evaluates its `card_id`, and lands it in
`tcg-silver/data/{region}/{event_id}.parquet` via the writer's normal
collision-check path.

### Key design decision: no SQLite writes, no bronze mutations

The `parqueted` column in `fact_events` is **not** a "row is in silver"
signal — it's a "this row's bronze parquet exists" signal set at scrape
time. So no `is_parqueted=0` flip is needed. The reconciler is a pure
function of MinIO state; the only side effect is deleting from
`tcg-silver/quarantine/`.

This was a real surprise during brainstorming: the user's initial
intuition was to flip `is_parqueted=0` to make the next silver run
"see" the row again, but silver doesn't gate on `parqueted` (it lists
every bronze parquet unconditionally). Deleting the quarantine file is
both sufficient and simpler.

### Placement

The reconciler is **not** downstream of `sync_card_images` in the DAG.
The user runs `sync_card_images_job` manually about once per month; the
reconciler is idempotent and re-checks every quarantine row on every
silver_eu_orchestrator invocation. This way, a `sync_card_images_job`
run followed by the next `complete_eu_pipeline` run automatically picks
up the new cards and promotes the matching quarantined rows — no DAG
wiring between the two jobs.

### Production validation (2026-06-09)

Ran `complete_eu_pipeline` end-to-end. The reconciler logs:
```
DE reconcile: scanned=9  promoted=0  still_quarantined=9  read_errors=0
UK reconcile: scanned=63 promoted=0 still_quarantined=63 read_errors=0
```

0 promotions is the honest result — none of the 72 quarantined
`card_id`s are in the cards folder yet. They will start promoting
once `sync_card_images_job` adds the missing cards and a subsequent
`complete_eu_pipeline` runs. Spot-checked the DE quarantine samples:
typical `card_id`s are bare set codes like `"OP03"` / `"OP10"` (no
card-specific number), which is the existing "set-code-only" quarantine
case from `is_valid_card_id`.
