# Session 2026-06-16 (single-zyte-key + scraper exception tolerance)

## Branch
`2026-06-16-single-zyte-key`

## Goal

Two related problems from the user's report on 2026-06-16:

1. **Operational change:** the operator now manages a **single** Zyte API key
   externally. Multi-key rotation is no longer in scope. The current
   `ZyteSessionResource` (built for `ZYTE_API_KEY1..N` rotation with
   dead-key marking and "all keys exhausted/timed out" messages) is
   dead weight and actively misleading the operator.

2. **Scraper crash bug:** the previous session log flagged that "a single
   Zyte hiccup crashes the whole `complete_eu_pipeline` with no bronze
   or silver work done." The scraper handles `statusCode != 200` from
   Zyte by logging `STOP` and breaking — but it does **not** catch Zyte
   SDK exceptions (timeouts, `RequestError`, aiohttp cross-loop
   `RuntimeError`). Those propagate and kill the whole scrape asset.

## Done

### Diagnosis (systematic-debugging skill)

**Root cause of the misleading error message** (`All Zyte API keys timed
out (KEY1, KEY2, KEY3) at hard_timeout=120.0s`):

- Verified Zyte API key 1 in `.env` returns HTTP 403 from the Zyte API
  endpoint (`{"type":"/auth/key-not-found","title":"Authentication Key
  Not Found","status":401,...}`). Keys 2 and 3 returned valid 200
  responses.
- The aiohttp 3.13 cross-loop bug (`RuntimeError("Timeout context
  manager should be used inside a task")`) fires on the 4xx response
  *before* Zyte's 403 is processed by our code. Our `_try_get` (lines
  93-112) catches this `RuntimeError` and **mistakes it for a timeout**,
  then the rotation loop marks the key dead and rotates.
- With three keys, the user sees "All Zyte API keys timed out" — the
  real cause is "KEY1 returned 403, which the aiohttp 3.13 cross-loop
  bug misclassified as a timeout, hiding the 4xx."

**Root cause of the crash on a single Zyte hiccup:** confirmed by reading
`src/tcg_platform/defs/scrape_raw.py:_scrape_region` (lines 99, 149).
The `zyte_client.get(...)` calls are not wrapped in `try/except`. A
Zyte timeout or 4xx mid-scrape propagates and crashes the whole asset.

## Outstanding (post-this-PR)

- **Cross-loop bug fires on the first Zyte call in this environment.**
  The pre-created `aiohttp.ClientSession` (bound to whatever loop is
  current at first call time) is used from a different loop on
  subsequent calls. The aiohttp 3.13 `BaseTimerContext.__enter__`
  raises `RuntimeError("Timeout context manager should be used inside
  a task")` when the session's loop and the request's loop differ.
  This is a real architectural issue, surfaced clearly as
  `ZyteCrossLoopError` in the new code. Verified: calling the SDK
  *without* a pre-created session (let the SDK create its own per
  call) works fine (6.12s for `example.com`, statusCode=200). The
  pre-created session was the source of the bug.
  **Recommended follow-up:** drop the pre-created session from the
  resource, let the SDK create its own per call, and rely on the
  Python-level `future.result(timeout=api_timeout)` as the only
  hard timeout. The aiohttp `ClientTimeout` is a nice-to-have for
  clean error messages, not a correctness requirement.
  This is out of scope for this branch — the user's stated goal
  was "single key, no rotation, juice the API manually." The
  cross-loop bug is a separate, deeper fix.

- **No e2e of `complete_eu_pipeline`** — same as prior sessions.
  Verified up to the scraper layer with the live smoke test on
  `scrape_ebay_de_raw`. The orchestrator's nested `execute_in_process`
  is unchanged and still works for the happy path.

- **silver_eu_orchestrator** still has 4 sequential `execute_in_process`
  calls. Same factory pattern would apply for a follow-up. Not in scope.

- **M5-T2 (Dagster schedules)** still deferred.

- **The orchestrator's nested `execute_in_process`** is still
  load-bearing. With the new exception-tolerance in the scraper,
  the inner sub-job rarely raises now, but init errors (e.g.
  ZyteSessionResource init) still propagate through the nested
  execute. Out of scope for this branch.
